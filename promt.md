Hi Geoff, before I implement Bug 228, I found two things during investigation that I think you should know about right away — these are existing security gaps, separate from what you asked for:
There's a second, unguarded Users maintenance screen at /maintenance/cas-users — it's not linked anywhere in the app's menus, but it's a live page. Any user who knows or guesses the URL can add/edit/delete users, including granting themselves admin rights. This directly affects the premise of Bug 228 (that Users access is already locked down) — it's only partially locked down.
The existing "admin-only" protection for the Users screen is frontend-only. It hides the button/page in the UI, but the underlying API has no server-side check — any logged-in non-admin CRO could call the API directly (outside the app) and create/edit/delete users. A few of those API endpoints don't even require login at all.
Given this, I'd recommend we treat Bug 228 as a proper access-control fix — meaning the new Read-Only/Hidden rules for Libraries and CORE Exports need to be enforced on the backend too (not just hidden in the UI), and we should close the two gaps above (guard the hidden cas-users route, and add real backend enforcement) as part of the same effort. This is more thorough than a simple UI-hide, but it's the right way to actually restrict access rather than just cosmetically hide it. Let me know if you want me to proceed on that basis, or if you'd prefer the minimal frontend-only version for now with the gaps noted separately.
